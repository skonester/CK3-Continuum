# Experimental 1.19.0.6 → 1.20.0.3 migration (v0.4.2)

Open a **1.19.0.6 campaign** and add a separate **1.20.0.3 reference**. The app selects the new faith and rite profile automatically. Its internal identifier is `experimental-1.19.0.6-to-1.20.0.3`.

This profile is based on the supplied `barbaratheanointed1283_1.19_test_v0.3.2.ck3` campaign (1283.8.10) and `Petty_King_Murchad_of_Munster_1066_09_17.ck3` reference. Both are compressed text saves. They have the same 13,269 province IDs, but different title, faith, religion, and character IDs. Copying reference numeric IDs into the campaign would attach data to the wrong records.

## Implemented changes

1. Move `religion/faiths` to the root `faiths/database`, retaining every campaign faith ID, fervor, religious-head title, holy-site list, variables, and change history. Reference presentation defaults are matched by stable faith or rite names.
2. Create one rite and religious organization per campaign faith, using the campaign faith ID as the new rite and organization ID. Resolve rite heads through the campaign religious-head title's holder, rather than importing reference characters. Faiths that 1.20 represents only as rites become independent custom faiths here.
3. Rename explicit character `faith` to `rite` in living, dead, prunable, and unborn records. Preserve `secret_faith`: 1.20 still uses a faith handle for secret religion and rejects `secret_rite`. Convert county and holy-order `faith` to `rite`, and title `state_faith` to `state_rite`. Values retain their campaign IDs. Other faith references, including typed script variables, still refer to the retained faith database.
4. Convert tenet entries to the target `tenet`/core-status shape, retain other doctrines, and convert the former monasticism tenet to the monasticism doctrine. Keep campaign colors and religious data.
5. Convert holy-site records, matching the reference site by stable name and resolving its barony through the campaign title key. Rebuild site faith lists from campaign faiths and begin with empty inventories. No donor relics or artifact handles are imported. Sites absent from the reference retain their IDs and receive an unbound barony, with an `unresolved-holy-site` journal entry and report warning.
6. Rename `scholar` to `erudite` and `poet` to `lifestyle_poet` in the lookup only. Preserve lookup positions, character trait indices, and XP bytes.
7. Initialize empty clerical-region, lease, saint, house-relation, barter, great-project, and situation sub-manager state. Update the synchronized metadata copies to version 1.20.0.3 and `save_game_version=17`.
8. Restore missing camp/estate `owner_title` handles from reciprocal campaign title `domicile` links. Preserve owned domicile IDs, locations, buildings, and resources. Unowned records without any title link become `none` database slots, with an explicit journal entry and report warning. Conflicting owners, multiple owning titles, and dangling title-to-domicile links are rejected. See [the crash investigation](domicile-crash-1.20.md).
9. Flatten old temporary-opinion `converging` state into `modify` and optional `days`. Copy the original adjustment, including fractional values, and explicit total duration; discard the obsolete elapsed-day counter. Opinions without an explicit total duration continue to use their definition's monthly change. Preserve cached values, start/expiration dates, owners, targets, relationships, and punishments. Constant opinions initialize `modify` from their saved value; already modern opinions remain unchanged.
10. Recover blank contract groups using campaign subject governments. Map obligations and selected levels by historical names, including valid groups with shifted indices. Use target defaults for newly introduced obligations. Recognize the two- and three-obligation administrative layouts. The supplied campaign also has 1,741 blank republic contracts with an incompatible five-slot layout. Those use the target's single fixed republic obligation, with a `contract-republic-default` journal entry and report warning; 16 of those records contain nonzero malformed selections that cannot be transferred.
11. Replace old accolade primary/secondary attributes with `types`, retaining their identities, glory, owners, acclaimed knights, successors, names, and history. Allocate the old glory rank alternately to primary and secondary, capped at three levels each and with a minimum of one each to retain both acquired attributes after glory loss. Remove obsolete icon fields. Combine old active/inactive owner lists into `accolades`, retaining their IDs and existing knight assignments. These are explicit migration policies: bonuses can differ, previously inactive knights may reactivate, and vacant records may become eligible for automatic succession. Barbara has 64 formerly inactive IDs across 58 owner lists: 53 vacant and 11 with existing knight references. No replacement knight is chosen by the converter.
12. Rename culture `exposure_marker` to `spread_marker`, retaining the source culture and fascination; remove obsolete `exposure_type` and empty `none`. Rename `innovation_bombard` to `innovation_gunpowder` in innovation records and markers while retaining progress. Rename character `scholar_perk` to `erudite_perk`. Reject alias collisions rather than merging distinct records.
13. Remove only queued `bp2_parent_guardian_hostage_taker_pulse` and `faith_fervor_events_pulse` instances, which have no current on-action definitions. Preserve unrelated scheduled events and script variables. Remove empty character modifier records, artifact modifier tokens, and game-rule settings; synchronize both metadata copies.

Existing characters, families, titles, ownership, histories, cultures, provinces, regiments, wars, and queued events are retained outside these specific patches. Portrait versions, DNA, DLC selection, campaign date, and player identity are preserved. The writer verifies every changed and unchanged byte span, metadata synchronization, archive addressing and CRC, and output readback. The separate journal includes both input hashes.

## Limits and rejection rules

This is a **schema migration candidate**. v0.4.1 advances at least 33 days and exits normally after the domicile fix. v0.4.2 adds the cleanup above and still needs a fresh CK3 load/simulation/save/reload test. The independent faith arrangement preserves campaign identity; it does not reproduce the target version's merged churches. Clerical elections, bishops, leases, saints, organizations, holy-order naming, active situations, and other new systems need engine testing and may need further rules. Missing source affiliations remain absent. New poet XP, portraits, source mods, and removed content definitions are not reconciled. Unknown modifiers, regiment types, story cycles, and title templates remain for individual content mappings. The previous error log appears capped during loading; reducing its schema errors should expose additional issues. See [the cleanup review](error-log-cleanup-1.20.md). The supplied campaign has an unmatched `segrada_familia` holy site, which remains unbound.

The profile refuses other version pairs, unexpected save schema versions, different province ID sets, duplicate database IDs or stable identities, mixed legacy/target structures, dangling explicit faith/accolade IDs, unresolved reference baronies, conflicting aliases, and unknown contract groups or historical obligation layouts. It requires source schema 15 or 16 and reference schema 17. Existing-file refusal, stale-source checks, container restrictions, and the 512 MiB limits apply unchanged.

Older profiles still cover 1.16.1–1.18.x → 1.19.0.6. Use that path first for an older campaign, then add a fresh 1.20.0.3 reference for this profile. The bundled 1.19.0.6 reference cannot serve as the 1.20 reference.

## Reproduce and test

```powershell
node scripts/create-test-candidates.mjs "C:\path\barbara-1.19.ck3" "C:\path\murchad-1.20.ck3" "C:\path\new-output-folder"
npm run test:desktop -- "C:\path\barbara-1.19.ck3" "C:\path\murchad-1.20.ck3"
```

The candidate script creates writer controls for both inputs and a migrated save/report without overwriting existing files. The desktop smoke checks the real app workflow, reference/version guards, publication, cancellation, and original hashes. Automated checks are recorded in [validation](validation.md).

In CK3 1.20.0.3, test the modern writer control first. Then load Barbara's candidate, inspect her realm, family, portraits, counties, religious heads, and holy orders, advance one day and one month, save, exit, and reload. Check church politics and succession before continuing the campaign. Keep the original saves and conversion report.
